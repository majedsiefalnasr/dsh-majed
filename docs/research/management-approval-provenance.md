## Conclusion

The inspected public connection contract supports native **Owner-only exact Fetch admission**. It does **not** provide a trusted server-side local-versus-remote source to that Fetch callback. Owner identity and Approval provenance are different requirements: the approved plan requires Approval from both local and remote GUIs, with trustworthy audit/source labeling, not a local-only Approval policy. Do not weaken Owner admission, infer provenance from `Origin`, accept a client label, or misreport the remote proxy's loopback hop as a local approval.

The decisive installed implementation is `if (peer.principal.kind !== "owner") ...403; return route.fetch(request)`: the carrier checks the admitted principal but passes **only the Request** to the exact Fetch handler. All authenticated browser requests share one Owner Peer, including the remote plugin's browser-authenticated inner requests. The remote proxy intentionally replaces outer transport metadata with loopback-shaped facts. These facts establish the limitation at this seam, not a general claim that authentication or remote management is unsupported. See [exact dispatch](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L820-L853>), [shared Owner admission](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L692-L750>) and [proxy header construction](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/loopback-proxy.ts#L58-L84>).

## Installed request trace

### Native admission: supported contract, not live verification

1. The Host/Origin fence runs before authentication. It accepts loopback, the listener's bind IP or configured trusted authorities, rejects cross-site Fetch metadata and mismatched attached Origin. Its own documentation explicitly says this fence **never establishes identity**. An allowed authority is neither Owner authentication nor evidence of the request's original locality: [trust rationale](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L133-L146>) and [fence implementation](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L233-L269>).
2. Native browser authentication verifies a signed authority-bound cookie and validity interval; the browser-cookie version is distinct from the API-operator version. `admit(request)` returns the shared Owner `browserPeer` for valid browser authentication, otherwise resolves a live API Peer or returns 401. Trust failure returns 403. No loopback-authentication exemption is present: [cookie verification](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L540-L569>) and [admission](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L692-L750>). The package also documents no Authorization-header token acceptance on this carrier: [native authentication contract](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/README.md#L38-L51>).
3. The mounted `/api` route calls `admit` before the `connection/request` waterfall and bridge. The bridge makes a WHATWG Request from method, string headers, body and disconnect signal, with a synthetic `http://dsh.internal` base. It does not attach socket address, original transport identity or a provenance object: [mounted route](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L1044-L1058>) and [bridge](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L40-L88>).
4. Exact routes match pathname and declared method, enforce `peer.principal.kind === "owner"`, then call `route.fetch(request)` without Peer/context/transport metadata. Routes belong to the registering fiber and disappear on disposal. Therefore a plugin using this public registry can rely on its native Owner admission, but cannot recover trusted original locality from the callback parameters: [exact Fetch implementation](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L820-L853>).

### Paired remote path: authority survives, original provenance does not

The remote plugin documents paired access as a full-control credential. For `/remote/...`, `pairedDeviceIdOf` requires a live device credential through the cookie or credential header; `service.touchDevice(id)` validates it. Before proxying, the handler enforces that gate, allowed methods, safe prefix rewriting, local-only exclusions and a bound local port. This is a server-side pairing check, not evidence that a raw header string is inherently trustworthy: [remote gate and dispatch](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/remote-api.ts#L126-L195>).

After the gate, the HTTP proxy constructs a new header set: loopback Host, synthetic `sec-fetch-site: same-origin`, selected content headers and its inner native browser-auth cookie. It does not forward original Origin, pairing credential, original address or a trusted local/remote marker. It targets `127.0.0.1` and forwards method/path/body. Consequently both outer LAN and tunnel use of this channel are represented at the native route as an authenticated inner browser request, not a distinct remote principal: [proxy implementation](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/loopback-proxy.ts#L35-L84>). The inner-auth implementation redeems the process launch URL and caches the native cookie; this was **read as code only, not executed during this research**: [inner-auth implementation](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/inner-auth.ts#L30-L85>).

The remote prefix is stripped before forwarding, so `/remote` is not observable at the exact native route. The remote plugin has explicit local-only control planes, but ordinary Majed management endpoints are not automatically one of those exclusions: [rewrite](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/remote-api.ts#L101-L115>) and [local-only policy](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/remote-methods.ts#L64-L89>). This does not authorize implementing a different local-only policy.

The optional `remoteWebUiPairing.isPairedDevice(request)` service consumes an incoming Node HTTP request and returns a boolean; it is documented for routes outside `/api`. It is not an attestation attached to the downstream WHATWG Request after this proxy has removed the outer pairing credential: [pairing service contract](</Users/majedsiefalnasr/.dsh/profiles/desktop/node_modules/@linxin666/dsh-remote-web-ui/src/pairing-access.ts#L1-L35>). Consulting it at an unrelated outer route or patching proxy internals is not proof that exact Fetch already exposes provenance.

## Owner, session and project scoping are separate

Native RPC retains a Peer: the generic RPC handler receives `(endpoint, payload, request.signal, peer)`, unlike exact Fetch. Gateway requests carry namespace, method, args, signal and Peer. Peer identity governs a connection scope, not an implicit project-directory authorization token: [RPC dispatch](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L888-L915>), [Gateway request](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-api-gateway/lib/index.js#L1460-L1472>) and [Peer scope](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-client-connection/lib/index.js#L646-L683>).

Remote access policy explicitly allows Owner; non-Owner resource/action policy is a different layer. Exact Fetch only supplies its Owner gate, not automatically generated project/session validation or a Remote invocation context: [policy decision](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-api-remote-access/lib/index.js#L206-L239>). `principalOf(ctx.invocation)` deliberately returns undefined for Owner and trusted in-process code; it cannot distinguish local and remote Owner approval: [principal helper](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-typert-protocol/lib/index.js#L283-L297>).

Native session APIs separately resolve session/agent identifiers and configure the agent Context lookup; resolving can resume an agent and applies native ownership/error handling. A guessed session ID is not proven scoped merely because the Fetch callback is Owner-admitted: [session lookup](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-api-session-controller/lib/types/agent.js#L174-L249>). Native session creation also rejects simultaneous workspaceId/cwd, resolves a registered Workspace, derives cwd from that Workspace, and checks reuse against membership/archive rules: [creation scope handling](</Applications/DeepSeek Harness.app/Contents/Resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-api-session-controller/lib/types/commands.js#L106-L148>). A future Manager must explicitly resolve its supported session/project relationship, canonicalize the intended writable scope and bind the reviewed content/challenge to it; this research has not proved that Manager flow. Skill scope/cache keys likewise are not authentication.

## Disposition and recommendation

**Supported by installed source, with a limited synthetic dispatch check:** public exact Fetch registration and native Owner-only dispatch, pre-authentication request fencing, cancellation/body bridge, fiber cleanup and isolated Skills registry invalidation/scoping behavior. These are candidate seams, not a complete live Management proof.

**Unsupported at the inspected exact Fetch seam:** trusted original local/remote Approval labeling, original remote-device identity, or a trusted origin attestation derived from Owner/browserPeer, URL, Origin, client headers or loopback socket facts. Even merely exposing the existing shared Peer to the callback would not restore metadata already removed by the remote proxy. A server timestamp could label receipt time, but would not establish locality.

**Unproved, not declared impossible:** real local/paired-remote browser admission and management parity, actual Settings/client rendering, authenticated Manager session/project validation, native Skills filesystem watcher/catalog propagation and official MCP lifecycle. No real API calls, login, provider/judge calls, account access, host restart, installation or installed-state change were performed by this research. The parent's fixture does not substitute for these acceptance checks.

Keep the dependent Command-hook Approval provenance path paused for an Owner scope decision or a supported upstream contract. Prefer an official admission/transport attestation propagated through the public connection API and paired remote proxy, authenticated and immutable against client spoofing, with defined local/remote meaning and request lifetime. Any future proof must preserve both local and remote Approval, native Owner admission and canonical content/scope binding; include forged-label and proxy-path negative tests. If that contract is unavailable, report the requirement as unsatisfied rather than silently record `local`, invent trust, patch DSH, intercept private methods or downgrade the requirement. Independent work may continue after its own prerequisites. This report does not claim or close T02A, and the unsupported provenance result remains a separate Owner decision gate.
