## Prepared-dispatch revocation increment — 2026-10-26

The adapter previously checked account/independent-entry availability only before credential and attachment preparation. A retained attachment read could therefore complete after removal and still send the already-held token. Each provider send now rechecks the bound account and pinned-entry consent after asynchronous preparation, including the bounded authentication retry; it never selects a replacement account. Already-dispatched requests are not cancelled or replayed by this change.

At the approved native adapter/controlled-transport seam, `account removal during attachment preparation prevents a prepared direct dispatch` failed before implementation with `AssertionError [ERR_ASSERTION]: Missing expected rejection.` It passes after the change and asserts zero Responses sends. The pinned-entry revocation companion also passes with zero sends. The initial red invocation first encountered missing worktree dependencies (`ERR_MODULE_NOT_FOUND`); linking the existing repository dependency installation resolved that environment issue before obtaining the behavioral red.

Verification: focused account/direct suites passed (24 tests before the pinned companion); `npm test` passed 500 Node tests plus the existing 166/166 classification assertions, with packaging/lifecycle checks included. The isolated `--codex-direct` native Settings product scenario passed on DSH `0.2.1-rc.3` / Node `v24.21.0`, with six of six listeners closed. This is controlled temporary-storage evidence, not an installed plugin update, host restart, real login or live provider dispatch.

Residual R01/R02 acceptance gates remain browser layout/keyboard/theme/font and full Arabic visual acceptance, actual desktop/paired-remote operational use after an approved restart, real account/login/refresh/dispatch under separate consent, and exact rc.2 compatibility.
