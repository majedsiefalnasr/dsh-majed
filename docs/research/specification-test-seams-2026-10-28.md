## One primary behavioral boundary

Prefer the complete **Owner action in native DSH UI → admitted production RPC/Fetch → feature service → actual native consumer → visible result**, rather than separate tests of every private helper. For request-driven behavior, start with the actual native session/tool lifecycle rather than inventing an event. Use the existing native mounted-product harness and controlled transports/temporary stores wherever applicable. A runner or helper passing is not proof of a feature it does not actually compose.

Use lower boundaries only for deterministic races, exhaustive policy decisions, protocol parsing and resource limits that cannot reliably be triggered through the primary workflow. Verify observable outcomes: actual dispatch count and route, effective tool/skill availability, retained state after remount, denied side effects, cancellation settlement and cleanup. Avoid tests that merely search source text or assert internal call order unless that order is itself the public contract under investigation.

Separate evidence layers:

1. **Portable regression:** built production client/host with declared fixture adapters and disposable state; deterministic positive, negative and race cases.
2. **Exact-host controlled integration:** unmodified versioned public DSH services, native transport/admission, synthetic pairing and controlled provider/MCP endpoints; report source hashes and release resources. It is not real-device or live-provider proof.
3. **Real browser acceptance:** actual rendered desktop/browser/mobile workflows, Arabic/English, light/dark, typography, narrow layout, keyboard/touch, draft/reading-position preservation and recovery. jsdom does not prove geometry, permission prompts or OS notification delivery.
4. **Operational acceptance:** separately approved installed rollout/restart, real accounts/devices/services, bounded live consumption and reversible Cutover. Approval of this proposal does not authorize these operations.
