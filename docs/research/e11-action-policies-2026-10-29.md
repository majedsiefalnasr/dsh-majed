# E11 reviewed local Safe/Aggressive action policies (2026-10-29)

Ticket #91, spec stories 29-33. Scope: the deterministic local slice only. The command analysis is best-effort lexical analysis of a documented subset; anything outside the subset checkpoints. Contextual judgment (E12) is out of scope. This change is PARTIAL: the ticket stays open.

## What was built

- `modules/command-policy/index.js` (pure, Node built-ins only):
  - `decide({ mode, request, settings })` returns `{ decision: 'allow' | 'checkpoint' | 'deny' | 'defer', reasonCode, effects[], origin: 'local-policy', reason }`. `origin` and `reason` are fixed redacted strings; no command text, path or target is ever returned.
  - `createPolicyLedger({ getMode, getEpoch, isLive, settings, now })` keeps a bounded in-memory decision history (last 100 per session) and fences stale/cancelled results.
  - `normalizeSettings` is the only way Owner settings enter the policy.
- `modules/command-mode/index.js`: `createCommandModes(isLive, { settings, now })` now also exposes `evaluate(sessionId, request)` and `policy` (the ledger). `set` (even to the same mode) bumps a per-session epoch, `reset`/`resetAll`/closure drop the mode and bump it, so pending decisions made under a previous mode are fenced. `reset` can only reduce to Ask me and also clears that session's history and counts (the replay id set is kept); closure and `resetAll` clear the whole ledger entry. `applyCommandMode` is unchanged and returns the same object.
- No route was added. The existing Fetch route accepts exactly `snapshot` and `set`; an `evaluate` action is rejected as `invalid_request` (tested). Reason: a route would need a trusted source for `projectRoot`, `home`, `knownScripts` and the task context; the Owner-admitted browser must not supply those, because that is exactly the project/agent-content widening this ticket forbids. Evaluation stays host-side and module-level.

## Rules (all by effects/targets/paths/known contents, never by command or wrapper name)

- `ask` or any unknown mode: `defer` (`mode_ask`). Any `request.kind !== 'command'` (browser, MCP, tool, hook): `defer` (`not_command_request`).
- Safe allows: reads and edits inside the project (and the temp directory), git local operations (add/commit/branch/merge/switch/tag/stash), known-effect test/build/dependency commands, an ordinary push in an Owner-trusted project, `rm` of regenerable output when the FIRST path segment under the project is regenerable (`node_modules`, `dist`, `build`, `coverage`, `.cache`, ...; `build/src` or `src/build/gen` checkpoint), single non-config file removal, and cleanup inside a temp directory that the host lists in `request.sessionTempDirs`.
- Safe checkpoints (request-specific; stored mode untouched): `git branch -D`, database drops, force/delete pushes, `reset --hard`/`clean`/`checkout --`, deleting non-regenerable project paths and config files, `rm -d`/`rmdir`/`unlink`, `mv` of project sources, recursive `chmod`/`chown`, history rewrites and forced ref moves (`branch -f`, `checkout -B`, `switch -C`, `tag -d/-f`, `rebase`, `reset <rev>`/`--keep`/`--merge`, `checkout <rev> <path>`, `commit --amend`, push to a different ref name, `--no-verify`), any write to `.git/`, writing/removing outside the project, recursive deletes in a temp directory the session did not create, network, process signalling, privileged, publish, global/installer commands, unknown commands and unknown scripts.
- Aggressive = Safe plus task-authorized, known-target destructive project actions: the host-attached `request.task.authorizedTargets` (`path:`, `branch:`, `db:`, `push:<remote>/<ref>`, `rollback:worktree`) lift only the matching destructive checkpoint. Unmatched targets stay checkpoints.
- Denied in both modes (never lifted): credential/key/Keychain/`.env` paths and commands (compared case-insensitively, including `rev:path` such as `git show HEAD:.env`, `$'...'` quoting, and `jq env`/`ps eww`), `env`/`printenv`/bare `set`/`export`, `rm` of `/`, home, system directories, the project root or its ancestors, explicit task prohibitions (`task.prohibitions`: `path:`, `effect:`, `branch:`, ...; a malformed prohibition disables every task authorization; prohibitions apply to every path-like argument including git pathspecs), and Owner `denyEffects`/`denyPaths`.
- Compound/script handling: a bounded POSIX shell subset tokenizer splits `&&`, `||`, `;`, `|`, newlines and tracks `cd`. `$()`, backticks, `(...)`, process substitution, heredocs, unresolved variables, globs in destructive targets, brace expansion, unquoted-risk environment overrides, bare shells, `curl | sh`, glob segments followed by `..`, and unquoted globs that could expand to credential names checkpoint. Pure-read commands use mixed flag policies: `sort`, `sed`, `rg` and `git grep` have flag validation, while most read-only Git subcommands rely on deny-lists rather than complete allow-lists; unmodeled flags remain a gap. Tooling flags that run code or redirect output (`go test -exec`, `pytest -p`, `node -e`, `--outDir`, `--prefix`, `--manifest-path`, ...) checkpoint in `--opt value` and `--opt=value` forms. `sh -c "<text>"`, `env`, `nohup`, `time`, `nice`, `timeout`, `command`, `sudo` and absolute system-binary paths are unwrapped and the inner command is judged. Script files and `npm run`/`npm test`/`make` targets are judged by `request.knownScripts` contents (recursively, depth 4, cycle-safe, total size capped at 64 KiB) or checkpoint as `unknown_script`. npm/pnpm/yarn also analyse `pre<name>`/`post<name>` and install hooks; extra positional arguments after a script name, arguments after `--`, `--exec` and `make VAR=value` checkpoint. The most restrictive finding wins.
- Trusted Settings (`settings`) can extend (`trustedProjects`, `knownEffects` limited to the safe classes read-project/write-project/vcs-local/build/test/dependency and still needing an in-project cwd) or tighten (`checkpointEffects`, `denyEffects`, `checkpointPaths`, `denyPaths`, `aggressiveDestructive: false`). Garbage, inherited or oversized extending settings are ignored (they grant nothing); a malformed or oversized TIGHTENING list (`denyEffects`, `checkpointEffects`, `denyPaths`, `checkpointPaths`, `aggressiveDestructive`) checkpoints with `settings_invalid` instead of shrinking silently. Request-supplied `settings`/`policy`/`approved`/`mode`/`trusted...` fields are never read (tested). Task authorizations are bounded (64 entries, strictly inside the project, no globs, no sensitive paths, not the project root).
- Ledger: per session, last 100 entries of `{ seq, requestId, at, mode, decision, reasonCode, effects, state }` plus counts; the request is held only as a per-process keyed HMAC for revalidation, never exposed. History is cleared by `closeSession`, `clear`, `resetAll`, `reset` (history and counts only) and by a liveness check on read; closed sessions are also pruned on every evaluate. Fencing: `authorize` (one-time claim: second claim gives `already_claimed`), `resolveCheckpoint` (strict boolean, resolves once, deny never overridden, approval is for that request only) and `cancel`; a separate ids-only replay set (1000 per session, oldest evicted first, not cleared by `reset`) keeps claimed/cancelled/rejected ids rejected (`request_id_reused`) after the 100-entry history evicts them; request ids are host-chosen and unordered, so an id evicted after more than 1000 later resolutions can no longer be recognised; late results after cancel, supersession, mode event (including an ABA return to the same mode), Owner settings change, request/script/cwd change, session closure or eviction are rejected.

## Limitations (exact)

- Controlled-fixture evidence only: pure functions and an in-memory ledger. No real browser, installed host, paired device or real native session was used; mobile testing is deferred to the Owner.
- Native consumption is UNPROVEN (gate G2): nothing here calls `decide` from a real native `approval/request`, and nothing answers a native permission request. The Owner action -> native consumer -> visible outcome acceptance criterion is not met. This must be recorded as an open gap on #90 and #91.
- No judgment (E12): unknown effects only checkpoint; no model, network or provider is used. No call counts for judgment exist yet (the ledger counts local decisions).
- The analysis is best-effort, lexical, and covers a documented subset of POSIX shell; it is not proven exhaustive, and hostile input outside the subset is only as safe as the checkpoint fallback: no symlink or filesystem resolution (`request.projectRoot`, `cwd`, `home` must be host-supplied absolute paths), no Windows paths, no other shells' syntax, no alias/function/PATH resolution beyond system-binary directories. Anything outside the subset checkpoints; a command that merely resembles an allowed one but uses an unmodelled flag is the main residual risk.
- `request.knownScripts` and `request.task` are host-attached inputs. This repository does not yet have a host source for them (task boundaries, script contents); a caller that passes model/project-controlled values there would widen authority. Wiring them is part of the missing native seam.
- Trusted Settings are a function/object passed to `createCommandModes`; there is no Settings UI or persisted Owner store for them yet.
- The visible redacted origin/reason/call-count presentation is not built (only `history`/`counts` data exist).
- No route exposes `evaluate`; no client change was made; no `~/.dsh`, installed package, network or provider access occurred.
- Known remaining gaps in the analysis: read-only git subcommands mostly use a deny-list of output/exec flags, so unlisted write/exec flags may remain; `git grep` uses an allow-list, while `sort`, `sed` and `rg` also have flag validation. `node --test` accepts unknown long flags and is not a full allow-list. `find . -print` is allowed; `find` with unmodelled expressions such as `-exec` checkpoints, as do `awk` and similar unknown commands. Symlinks inside the project can make a lexically in-project path point outside it. Git pathspec and rev:path analysis is lexical, not full Git path resolution.
- Replay fence: ids evicted after more than 1000 later resolutions in one session can be evaluated again; the fence is in memory, per process, and ends with session closure.
- `request.sessionTempDirs`, `request.knownScripts` and `request.task` need a trusted host source; a caller that passes model- or project-controlled values widens authority.
