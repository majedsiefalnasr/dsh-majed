## How to use the ledger

Each stable row is one acceptance unit, not a passed test. `P` means **source identified; implementation and automated characterization pending; desktop/local pending; paired-remote pending**. `D` means an **explicit approved deferred planning ticket**, still unimplemented and unverified; publication approval is not an individual waiver of a needed capability before removal. `O` means **pending Owner scope/disposition**: no approved ticket cleanly covers the behavior or there is a material contract conflict. It is not an invented deferral. Every row's implementation ticket is its evidence owner; a row with several tickets requires all named owners to coordinate its fixtures. No automated, desktop or remote parity result is claimed by `P`, `D` or `O`.

When implementing, replace the pending text with dated evidence links and versions: fixture/test name and command/result; desktop-after-restart result; paired-remote result; limitations and Owner disposition. Preserve row identity. Native basics must use distinct Majed state/route/slot identities, Owner-admitted public seams, native tokens, English/Arabic RTL and independent module disposal. T02A–T02E prove exact-host seams; source citations do not pass those gates. T28M/T28S prepare reversible single-owner Cutover; T29/T30 own actual acceptance. Required missing rows block affected Cutover/removal unless the Owner explicitly accepts a documented deferral. D10 never authorizes automated reference removal.
