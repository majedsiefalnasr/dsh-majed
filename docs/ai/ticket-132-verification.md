## Behavior and decisions

- Login: no `method` imports Claude Code's login when present, else starts browser authorization; `method: 'oauth'` always starts browser authorization and never reads Claude Code's store; `method: 'keychain'` requires the import. Anything else is rejected (`payload.method must be "oauth" or "keychain"`; Codex rejects any method). Credential reads happen only on these explicit actions and when an imported account refreshes.
- Imported accounts are `keychainBound`; only they sync. Sync = on refresh, prefer a fresher token already in Claude Code's store, otherwise refresh and write back only the three token fields, only if source identity was not rejected/unproven and the store still holds the access token the refresh started from (the low-level token check is inherited; the identity guard is owned remediation; OAuth accounts never write there). A single interval every 5 minutes re-reads bound accounts; it is cleared on dispose, `unref()`ed and idle when Claude registration collided. The binding (`keychainBound`) survives every sync and refresh, so later refreshes keep syncing.
- Account identity (second remediation, deviation from the reference): a token found in Claude Code's store is adopted only when it provably belongs to the same account, i.e. the emails are equal after `trim().toLowerCase()` on both sides (the Codex store's normalization). Real Claude Code blobs normally carry no email and Anthropic issues a new refresh token on every refresh, so refresh-token continuity cannot identify an account the `claude` CLI refreshed first. When the stored session or the source lacks an email, it is resolved through the existing profile lookup (`fetchClaudeProfile`, `CLAUDE_PROFILE_URL`): the stored side with the stored access token, the source side with the SOURCE access token. Each lookup is bounded by a 5 s timeout and the component lifecycle signal. The email is recorded on the stored session at import and whenever a refresh learns it, so later comparisons are cheap. If a lookup fails, times out, is aborted or returns no email, the source is NOT adopted and the store is NOT written (the stored account refreshes its own token); an abort is rethrown as an abort, never as `invalid_grant`, so no account is deleted. Refresh-token continuity remains only as an extra signal when no email is known on either side after the lookups. A source that is not adopted is never written back at all (previously write-back relied on the token mismatch). A different account needs an explicit new import (Import Claude Code on the card).
- Disposal (remediation): disposing the component aborts a lifecycle signal. Pending ticks stop, a refresh in flight is aborted (the request carries the signal), and nothing is read from or written to Claude Code's store, and no session is saved, after disposal.
- Tokens exist only in the protected store; status carries account label, plan and expiry only. Error text goes through `browserSafeError`. Tests assert no fixture token appears in any RPC response, error or listing.
- OAuth: authorize URL has PKCE S256, `code=true`, a 32-byte state; callback state is verified by the shared flow manager; the card opens the returned URL with `window.open(url, '_blank', 'noopener')` only after the RPC and only when the URL is non-empty.
- RPC validation: provider enum (`codex`, `claude`), method enum, `promptCacheTtl` enum (`5m`, `1h`), Codex-only endpoints (`speed`, `setSpeed`, `prepareReset`, `consumeReset`, image, proxy) reject Claude.
- Cache lifetime: Manage offers follow config / 5 minutes / 1 hour; choosing follow config removes the stored value; the effective value reaches the Anthropic request (reference tests).
- Isolation: the Claude card is wrapped in the owned error boundary; Claude registration collision leaves Codex and the Settings section working and disables only Claude login; the Claude card, like the Codex card, lives in the owned Settings section and disappears with the component. While the reference plugin is enabled the section stays and shows the coexistence message (spec story 6, "Coexistence"): both cards remain visible (accepted #128 side-by-side decision, unchanged since #129) and Claude login is disabled when registration collided. Only the composer surfaces (usage badge, Speed, `/fast`) are withdrawn while the reference serves.
- Registration (remediation): Claude registers the preference-aware adapter (`AccountPreferencesAdapter`) exactly as Codex does, so display name, model visibility and renaming, independent-account entries and pool routing reach the picker and chat. The account pool is assembled for both providers with the same bounded per-account discovery.

## Honest limits (NOT live-verified)

- No real Claude login, import, refresh, usage call, catalog call or chat was run. The real macOS Keychain and `~/.claude` path, the real OAuth redirect on `localhost`, Anthropic request acceptance (headers, beta flags, CLI version presentation) and real SSE streams are covered by fixtures only.
- Visual polish of the card was not checked in a real browser; render tests use fake React.
- Arabic copy is mine and not reviewed by a native speaker.
- `writeFileRaw` (credentials file fallback, reference behavior) refuses a symlink at the credentials path (hardening added in remediation), but the check, directory creation and write are not atomic: a link planted between the check and the write could still be followed. Residual finding pending live acceptance (single-user machine, own home directory); not an Owner-accepted risk. The macOS Keychain path does not use it.
- Sync identity limits: the blob has no stable account id other than a possible email. Adoption of an email-less blob needs a network profile lookup (Anthropic profile endpoint with the access token), so it is skipped while offline, rate-limited or when the profile has no email; the stored account then refreshes its own refresh token, which can fail with `invalid_grant` if the `claude` CLI already rotated it (re-import fixes it). It is NOT live-verified whether real blobs carry an email, whether the profile endpoint returns one for them, or how Claude Code reacts to our write-back.
- Inherited race (reference `writeBack`): the write-back is a read-modify-write of Claude Code's store (read blob, check the access token, merge three fields, write). The `claude` CLI can rotate between our read and our write and its newer tokens would be overwritten, which could invalidate its session until it logs in again. The check narrows but cannot close that window (no lock is shared with the CLI). Residual finding pending live acceptance, not an Owner-accepted risk.
- Email-only identity cannot distinguish multiple organizations sharing the same normalized email; no organization-id comparison is implemented. A failed email lookup followed by re-import can also create duplicate account entries. These are residual findings pending live acceptance.
- If source identity lookup fails while source tokens differ, the stored account can still spend its own stale refresh token; `invalid_grant` can remove the stored account and require re-import. Possible token-family reuse revocation is **UNVERIFIED**, not an established outcome.
- Source-backed timeout limit: the Keychain read has a 3 s subprocess timeout. A pending macOS prompt may outlast it, and fallback can reach browser authorization if no file login is available. This timing/prompt interaction is not live-proven.
- Some pre-existing Manage tests print React "key" warnings from their JSX mock; they are not failures.

## Second remediation (after the second independent review)

Finding P2: email-less imported sessions were adopted only when the refresh token was identical, but Anthropic rotates the refresh token on every refresh, so once the `claude` CLI refreshed first the rotated source was never adopted and we spent a stale refresh token (possible `invalid_grant`, which makes TokenManager delete the account, and possible token-family reuse revocation, which is UNVERIFIED). The stale-token spend mechanism was confirmed in fixtures, not live reuse revocation. Fix: identity by normalized email, resolved through the profile lookup when absent (see "Account identity" above), email recorded at import and when learned, no adoption and no write-back when identity is not proven, abort never treated as permanent. P3: Keychain prompt wording (Allow, not Always Allow; later prompts possible), reference-plugin step optional and Owner-approved, normalization of emails (case/whitespace), the writeBack race and the identity limits documented, live sync check added as an Owner observation. Regression tests (`test/claude-identity-132.test.mjs`) failed before the fix (6 of 11 failed against the previous source; the others pin the preserved safe behavior). Sync with the real `claude` CLI is NOT live-verified. Awaiting final focused review and Owner live acceptance.
